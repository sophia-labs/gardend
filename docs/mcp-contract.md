# Local MCP Contract

The native app exposes MCP through the loopback endpoint:

```text
POST /mcp
```

It is a local Streamable HTTP-style JSON endpoint for `initialize`,
`tools/list`, and `tools/call`. It is not a separate product backend. MCP tools
are adapters over the same local provider services used by Tauri commands and
REST routes.

## Contract Source

The local surface registry is:

```text
parity/local-loopback-surface.json
```

MCP tool definitions are implemented through:

```text
parity/local-loopback-surface.json
src-tauri/src/mcp_tool_catalog.json
src-tauri/src/mcp_tool_registry.rs
src-tauri/src/mcp_tool_dispatch.rs
```

The surface registry is authoritative for local MCP tool names and scopes.
Rust loads those scopes for `tools/list` metadata and call authorization, while
`mcp_tool_catalog.json` owns tool descriptions and input schemas. The inventory
gate checks every local MCP tool has valid scopes, catalog schema, and dispatch
coverage, and separately verifies the dynamic `crdt_operation` scope union
against the Rust operation-kind rules.

## Authentication And Scopes

There are no public MCP methods. MCP calls require a bearer token. Accepted
tokens are:

- The per-run compatibility session token from `loopback.json`.
- Active named client tokens from `loopback-client-tokens.json`.

`tools/list` exposes scope metadata for clients:

```text
_meta.sophia.local.requiredScopes
_meta.sophia.local.scopeMode
```

Dynamic tools also expose operation-scope metadata when the required scopes
depend on the requested operation kind.

Read-only scopes are default-grantable in the UI. Mutating and delete scopes are
consent-only for named tokens, even while the session compatibility token still
exists.

## Mutation Semantics

MCP mutating document and workspace operations must route through the CRDT
operation path. They should not directly edit document manifests, workspace
snapshots, RDF stores, or search indexes.

The intended flow is:

```text
MCP tool call
  -> input validation and scope check
  -> provider or CRDT service
  -> Yjs transaction
  -> projection flush
  -> hosted-shaped result envelope
```

This keeps MCP, REST, and Tauri behavior aligned and prevents side channels from
creating separate sources of truth.

## Current Tool Families

The current local MCP surface covers:

- Graph and document reads.
- Workspace reads and selected workspace mutations.
- Document writes and block-level edits.
- Wire reads and mutations.
- Lexical and semantic search.
- RDF query/load/dump/update.
- Local job access.
- Salience, memory, song, and orientation local extensions.

The exact list is generated by the running app's `tools/list` response and
tracked by the parity inventory.

## Acceptance Status

`parity/surface-contracts.json` is the contract-truth file for hosted-shaped
REST and MCP parity. It uses explicit `accepted` and `deferred` statuses:

- `accepted` means the schema and externally visible semantics are accepted for
  the current local contract.
- `deferred` means the surface may be implemented and enabled, but remaining
  behavior gaps are deliberately documented in `note` or `untestedReason`.

The inventory gate rejects accepted entries whose schema or semantics are not
accepted, and rejects deferred entries without a documented reason.

## Validation

Static contract checks:

```bash
pnpm parity:inventory
```

Live MCP checks with the Tauri app running:

```bash
pnpm parity:loopback
```

For behavior parity work, add or extend live probes before marking a hosted MCP
surface as semantically accepted.
